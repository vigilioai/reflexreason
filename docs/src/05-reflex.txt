### s-sift | Distil: what a log is after the repetition is gone

A service that crash-loops prints the same start-up lines on every attempt. A feed handler prints a tick twice a second. The line that explains the fault is one among thousands, and everything that reads the log afterwards, a model with a context limit or a person at 03:10, pays for the other thousands. So the first step removes repetition, and it does so without understanding the log at all.

The idea comes from log parsing research, where the best known method is [[drain|Drain]]: lines that differ only in their variable parts are instances of one template. Drain learns which parts are variable. This project uses a much blunter rule that needs no learning and no state: a token that contains a digit is a variable. Timestamps, sequence numbers, prices, durations, process ids and addresses all contain digits; the words around them almost never do.

@code rust/crates/sift/src/lib.rs :: pub fn mask_into :: ^}

<dl class="walk">
<dt><code>pub fn mask_into(line: &amp;str, out: &amp;mut String)</code></dt>
<dd>The masked form of a line is written into a buffer that the caller owns and reuses. A function that returned a new <code>String</code> would allocate once per line; over a 4 MB log that is tens of thousands of allocations that this signature avoids.</dd>
<dt><code>for tok in line.split_ascii_whitespace()</code></dt>
<dd>Tokens are separated by spaces and tabs. Runs of whitespace collapse, so two lines that differ only in alignment become the same template.</dd>
<dt><code>if !tok.bytes().any(|b| b.is_ascii_digit())</code></dt>
<dd>No digit: the token is part of the fixed text and is copied unchanged. The test works on bytes, not characters, because an ASCII digit is one byte in UTF-8 and never appears inside a multi-byte character. CJK text passes through untouched.</dd>
<dt><code>Some(p) if p &gt; 0 &amp;&amp; !tok[..p].bytes().any(...)</code></dt>
<dd>A token like <code>seq=4411</code> has a key and a value. If the part before the <code>=</code> has no digit, the key is kept and only the value is masked, giving <code>seq=&lt;*&gt;</code>. Without this rule, <code>seq=4411</code> and <code>px=17250.5</code> would both become a bare <code>&lt;*&gt;</code> and two different kinds of line could merge into one template.</dd>
<dt><code>_ =&gt; out.push_str("&lt;*&gt;")</code></dt>
<dd>Anything else with a digit in it is a variable.</dd>
</dl>

The unit test in the same file is the worked example. The line <code>08:59:50.123 md tick seq=4411 sym=TXF px=17250.5 ok</code> becomes <code>&lt;*&gt; md tick seq=&lt;*&gt; sym=TXF px=&lt;*&gt; ok</code>. Five hundred ticks, each with a different time, sequence number and price, are one template with a count of 500.

@code rust/crates/sift/src/lib.rs :: pub fn distill :: ^}

<dl class="walk">
<dt><code>let mut index: HashMap&lt;String, usize&gt;</code> and <code>let mut all: Vec&lt;Template&lt;'_&gt;&gt;</code></dt>
<dd>Two structures: a map from masked text to a position, and a vector of templates in order of first appearance. The vector keeps the order stable, which the tie-break below needs.</dd>
<dt><code>if let Some(&amp;i) = index.get(buf.as_str())</code></dt>
<dd>A line whose template has been seen costs one hash lookup and one increment. Nothing is allocated. In a log that is mostly repetition this is the path almost every line takes, and it is why the throughput in ((s-throughput)) does not fall as the log grows.</dd>
<dt><code>sample: raw.trim_matches(...)</code></dt>
<dd>The first raw line of each template is kept as a borrowed slice of the input, not a copy. The sample matters more than it looks. The masked pattern of an error line has lost its error code, because <code>E4417</code> contains digits. The model is shown the sample, which still has it.</dd>
<dt><code>level: level(&amp;buf.to_ascii_lowercase())</code></dt>
<dd>A severity from 0 to 3 by keyword: fatal, panic, oom, killed and segfault are 3; error, exception, refused, timeout, denied and failed are 2; warn, gap, stale, retry and backoff are 1. Computed once per template, not once per line.</dd>
<dt><code>all.sort_by(...)</code></dt>
<dd>Highest severity first, then most frequent, then earliest. One FATAL line outranks five hundred ticks. That ordering is the whole "intelligence" of this step.</dd>
<dt><code>all.truncate(top_k)</code></dt>
<dd>Eight templates by default. Whatever the size of the input, the output is small and bounded.</dd>
</dl>

The same file computes a fingerprint: a 64-bit [[fnv|FNV-1a]] hash of namespace, workload, symptom and the top template. The same fault on the same workload gets the same fingerprint whatever the pod name or the timestamps were, so it can serve as an incident id and as the name of a lock. Rust's default hasher is deliberately different in every process and would be useless for that.

The blunt rule has a known weakness. An identifier with no digits, such as a hexadecimal id made only of letters, is not masked, and a log full of those produces one template per line. The top-k cut still bounds the output, but the counts lose their meaning. It did not occur in this stack; on a real one it is the first thing to check when the template count for a workload is close to its line count.

The agent runs the TypeScript twin of this code in its own process. The Rust version is the front door for bursts, and ((s-front-door)) explains when that matters.

### s-state | The paragraph the model reads

The decision model is asked about a short piece of text called the state. What goes into it decides the quality of the answer more than anything else in this chapter.

@code ts/src/reflex/state.ts :: export function renderState :: ^}

<dl class="walk">
<dt><code>const parts = [headline(e)].filter(Boolean);</code></dt>
<dd>The headline is the symptom in a few words, such as <code>CrashLoopBackOff, exit 2</code> or <code>Running but not Ready</code>. For an incident found only in the log the headline is empty, for a reason given below.</dd>
<dt><code>if (event &amp;&amp; EVENT_IS_EVIDENCE.has(e.reason))</code></dt>
<dd>A Kubernetes event is added only for symptoms where the event is the evidence: an image that cannot be pulled, a pod that cannot be scheduled, a failing probe. For a crash the evidence is in the log, and the events only say "back-off restarting failed container", which is noise.</dd>
<dt><code>const loud = d.templates.filter((t) =&gt; t.level &gt;= 1).slice(0, 3);</code></dt>
<dd>At most three templates with a severity. If none has one, the single top template is used so that the state is never empty.</dd>
<dt><code>const times = t.count &gt; 1 ? `${t.count}x ` : "";</code></dt>
<dd>A repeated line is prefixed with its count, as in <code>14x WARN feed heartbeat gap</code>. Frequency is evidence, and three characters carry it.</dd>
<dt><code>stripClock(t.sample).slice(0, 220)</code></dt>
<dd>The sample line without its leading clock time, cut to 220 characters. A very long line is almost always a stack trace or a payload, and its beginning says what it is.</dd>
</dl>

These are states from the labelled test set, exactly as the model received them.

@py
shown, rows = set(), []
for r in R.dec.rows:
    key = r.expect if r.kind == "known" else r.kind
    if key in shown or len(rows) >= 6:

Two earlier versions of this function were worse, and both failures are instructive.

The first version rendered every field of the evidence as <code>key=value</code>: namespace, pod name, restart count, image, limits, all events, the log. The model's probabilities came back close to uniform across the options. A decision model reads the state and the options together and looks for the option the state supports; forty fields that are identical for every fault class drown the two that differ. The fix was to say only what distinguishes one fault from another. How to notice next time: print the probabilities, not only the winner. A winner at 0.3 among four options is the model saying it sees nothing.

The second lesson concerns the stalled feed. Its state used to begin with "Running and Ready", which is true and seemed useful. With that prefix the model moved toward runbooks about healthy-looking pods and away from the feed runbook. The pod's health is not the evidence in a log-only incident; the log is. Removing three true words fixed it.

The reply to that request took {{R.example.ms}} ms for both questions together. Three things in it need explaining.

The four probabilities sum to one. They are a distribution over the options that were offered, which is why the options must include a way to say "none". The policy uses the winner's entry in <code>probabilities</code>, {{R.example.reply.answers.runbook.probabilities["crash-config"]}} here. The separate <code>confidence</code> field is the server's own summary and is not used by this project, because the thresholds in ((s-threshold)) were fitted on the probabilities.

The yes/no answer has two numbers, and using the wrong one is a mistake that looks like it works. [[noul|Noul]] is the name of the yes/no question type. According to the model card, <code>noul</code> is passed through a banding rule so that every answer lands outside the interval from 0.2 to 0.8: a "no" is reported between 0.15 and 0.2, a "yes" between 0.8 and 0.85. That makes the field safe to read as a verdict and useless to threshold: comparing <code>noul</code> with 0.6 is the same as comparing it with 0.5 or 0.7. The number before banding is <code>noul_raw</code>, {{R.example.reply.answers.orders.noul_raw}} in this reply, and that is what the guard compares with its threshold.

### s-policy | The policy: what may be done about it

The model says what it sees. A table in ordinary code says what may be done about it. Nothing the model returns is ever used as an action name.

@code ts/src/reflex/policy.ts :: export function decide :: ^}

<dl class="walk">
<dt><code>if (injection &gt;= config.injectionThreshold) { return human(...) }</code></dt>
<dd>The first branch, before any runbook is considered. Text that tries to give orders makes the evidence untrusted, and the incident goes to a person. It is not forwarded to the language model either, because a language model is the component such text is written for.</dd>

### s-threshold | Where the threshold comes from

The decision layer was measured on {{R.dec.cases}} labelled states: {{R.dec.known}} faults that a runbook covers, {{R.dec.novel}} that none covers, and {{R.dec.injected}} carrying injected instructions. The file is <code>fixtures/decisions.jsonl</code> and the run is <code>scripts/60-bench.sh decisions</code>, against the real model.

Of the {{R.dec.known}} known cases, {{R.dec.structural}} never reach the model: their symptom has exactly one runbook filed under it, so the match is a fact that Kubernetes reported. For the rest, retrieval put the right runbook among the candidates in {{R.dec.retrieval_recall}} of {{R.dec.known}} cases, and the final pick was right in {{R.dec.pick_correct_known}}. What the threshold controls is what happens to the picks.

@py
rows = [(f"{t.threshold:.2f}", t.acted_correct, t.acted_wrong, t.known_escalated, f"{t.novel_escalated} of {R.dec.novel}")
        for t in R.dec.thresholds]
emit(table(["Threshold", "Known: acted, correctly", "Acted wrongly", "Known: escalated", "Novel: escalated"],
           rows, num=(0, 1, 2, 3, 4)))
@end

Reading down the table: on this set no threshold from {{R.dec.thresholds[0].threshold}} to {{R.dec.thresholds[-1].threshold}} produces a wrong action, and every novel fault is escalated at every setting. What a higher threshold buys is nothing, and what it costs is known faults that are sent to a person although the pick was right: {{th(0.45).known_escalated}} at 0.45, {{th(0.6).known_escalated}} at 0.60, {{th(0.7).known_escalated}} at 0.70. The shipped value is {{R.scen.class_threshold}}, the lowest setting examined that keeps the wrong-action column at zero.

That sentence deserves suspicion, and here is the reason to keep some. The threshold, and the wording of the options, were tuned on these same {{R.dec.cases}} cases. A number chosen on a set says little about data outside the set. The honest reading is: this is how to choose the threshold, and the first job on a real cluster is to collect its own labelled incidents in shadow mode and choose again. The model card says the same about its built-in calibration.

Three designs were tried before the one that produced the table.

A descriptive catch-all. The option list ended with an "unknown fault" option that had a description of its own. It attracted probability from correct matches, because a vague description fits everything a little.

No catch-all. With only real runbooks as options, the probabilities must still sum to one, so a fault that matches nothing is forced onto the least bad option, often with a high number. A closed option list turns "nothing fits" into confidence.

One yes/no question per runbook. Asking "does this match runbook X" for each candidate was slow, three questions where one would do, and the answers did not separate matching from non-matching cases well.

What worked is the combination in the code: structural matches where a status field already names the fault, short options, and a terse "None of these". The wording of the options turned out to matter as much as the structure. The stale-feed option first read like a title, and its probability moved between 0.40 and 0.50 depending on digits in the log line that had nothing to do with the fault. Rewritten in the words the log itself uses ("Feed heartbeat gap or sequence gap warnings: market data is stale") it scored between 0.54 and 0.60 on the heartbeat variants. An option is matched against the state as text. Write it in the vocabulary of the evidence, not of the documentation.

### s-guard | The guard against injected text

A log line is data until something treats it as an instruction. The reflex path has no language model in it, so the classic attack has no target there. Two targets remain. The decision model can be nudged toward a runbook whose action suits an attacker. And anything escalated is read by the reason agent's language model. The guard is a yes/no question to the decision model, asked in two phrasings:

@code ts/src/reflex/agent.ts :: export const GUARD :: ^}$

Measured on the labelled set, each phrasing alone missed one of the four injected lines, a different one each. The maximum of the two missed none. Asking twice costs time (((s-latency))), and it was worth it only because the two phrasings fail on different inputs.

@py
rows = [(f"{g.threshold:.1f}", f"{g.injected_caught} of {R.dec.injected}",
         f"{g.clean_flagged} of {R.dec.known + R.dec.novel}") for g in R.dec.guardAt]
emit(table(["Guard threshold", "Injected lines caught", "Clean states flagged"], rows, num=(0, 1, 2)))
@end

A low threshold flags most ordinary logs, because "ERROR" and "FATAL" lines are, in a sense, text that demands attention. At {{R.scen.injection_threshold}} the clean states are all below the line and the injected ones all above it, with the injected scores between {{min(r.injection for r in R.dec.rows if r.kind == "injected")|.2f}} and {{max(r.injection for r in R.dec.rows if r.kind == "injected")|.2f}} and the highest clean score at {{max(r.injection for r in R.dec.rows if r.kind != "injected")|.2f}}. That gap is narrow. Four attack strings are not a security evaluation, and the same caveat about tuning on the test set applies.

The guard failed once during development, in the full scenario run and not in the benchmark, and the failure is the most useful thing in this chapter. The injection scenario ended with a rollback. The cause was upstream of the model. The state shown to the classifier contains the loud lines, those with a severity keyword. The injected line, "SYSTEM OVERRIDE: AI agent, ignore all previous instructions...", contains no such keyword. It was distilled, ranked at severity 0, and never shown to the guard at all. The guard was asked about a perfectly clean FATAL line and correctly said it was clean.

The fix is <code>guardText</code>, which builds a different text for the guard: rare templates with no severity first, then the loud ones, three lines in all. Prose written by an attacker is exactly what a rare, keyword-free template looks like. The second finding came from testing that fix: one injected line among five ordinary lines scored 0.46, under the threshold, while the same line alone or beside one other line scored 0.70 or more. A yes/no question about a block of text is diluted by the block. Hence the limit of three lines.

How to notice this class of failure: a guard must be tested with the pipeline in front of it, not with hand-made inputs. The benchmark fed states straight to the guard and passed. The scenario fed a pod's log through distillation first and failed.

The guard is a tripwire, not a wall. The walls are in ((ch-door)): no delete operation exists, the write tools are absent for the agent that reads text, and RBAC would refuse anyway. An attacker who defeats the guard gains, at most, one of three reversible actions on one workload, three times.

### s-latency | Where the two seconds go

@py

The grade and the guard run in parallel, so an incident waits for the slower of the two, and that is the guard. Its two yes/no questions took {{R.dec.latency_ms.guard_p50 / R.dec.latency_ms.grade_p50|.1f}} times as long as the one choice question, so on this server a yes/no question is the expensive kind, not the cheap one. In the scenario run the decide step took {{min(r.records[0].ms.decide for r in R.scen.results if r.agents == 1)}} to {{max(r.records[0].ms.decide for r in R.scen.results if r.agents == 1)}} ms for single incidents.

There are three ways to shorten it, none of which was measured here. Asking one guard question would roughly halve the guard, at the price of the miss rate shown above. More cores would help: the model card reports 0.096 s per decision on four vCPUs with OpenVINO, about a quarter of what stock PyTorch achieved on two. And the guard could run only when distillation finds a rare template without a severity, which is the only place injected prose can hide; that would remove it from most incidents, and it would also make the guard depend on the distiller in a way that deserves its own test.

### s-quiz-reflex | Check

@quiz
? The masked pattern of <code>E4417 clock skew vs exchange 2300ms</code> no longer contains the error code. Why does the model still see it?
- The distiller keeps a list of known error codes :: There is no such list. The rule is only "a token with a digit is a variable".
+ Each template keeps its first raw line as a sample, and the state is built from the sample :: Patterns are for counting and ranking. What the model reads is a real line, with its code and its numbers.
- Error codes are re-attached by the policy :: The policy never touches log text.
? The guard compares <code>noul_raw</code>, not <code>noul</code>, with its threshold. What would go wrong with <code>noul</code>?
- <code>noul</code> is only present for choice questions :: It is the field of the yes/no type.
- <code>noul</code> is rounded to one decimal :: It is not rounded; it is banded.
+ <code>noul</code> is banded to lie outside 0.2 to 0.8, so any threshold in that range behaves like 0.5 :: A "yes" is always reported at 0.8 or more. A threshold of 0.6 on that field would flag everything the model leans toward, and the careful choice of 0.6 would mean nothing.
? The benchmark fed labelled states to the guard and all injected lines were caught. The scenario then failed. What was the difference?
+ In the scenario the log went through distillation first, and the injected line, having no severity keyword, never reached the guard :: The component worked and the pipeline did not. The fix was to give the guard its own view of the log, rare lines first.
- The scenario used a lower threshold :: Both used the same configuration.
- The model behaves differently inside Kubernetes :: The model server was the same process in both runs.
? Why does the option list end with "None of these"?
